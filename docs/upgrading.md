# Upgrading

Each section covers one release that needs more than a version bump. Upgrade
every ConnectRPC gem to the same version, as the
[support policy](support.md#match-the-connectrpc-package-versions) requires.
The [changelog](../CHANGELOG.md) lists every change.

## 0.3.0

### Breaking change: Steepfiles name core explicitly

Only applications that type-check with Steep or RBS are affected. The optional
gems' signature manifests no longer name connectrpc gems, because
`rbs collection` locks every manifest dependency as a standard library and then
fails to load the whole environment. Without `rbs collection`, an optional
library therefore no longer loads core's signatures. Add `library "connectrpc"`
beside each optional connectrpc library, and `library "connectrpc-async"` beside
`library "connectrpc-falcon"`:

```ruby
target :app do
  library "connectrpc"
  library "connectrpc-async" # Required by connectrpc-falcon.
  library "connectrpc-falcon"
  check "app"
end
```

Projects that use `rbs collection` now install every connectrpc package as a
gem in any Gemfile order and need no other change. Runtime behavior, generated
code and signature declarations are unchanged. See
[package APIs](rbs.md#package-apis-and-extension-contracts).

### Breaking change: Service#methods is now Service#rpcs

`ConnectRPC::Service.new` takes `rpcs:` instead of `methods:`, and the reader
is `Service#rpcs`. The old name shadowed Ruby's `Object#methods`, so reflection
on a service returned its declarations. There is no alias: `service.methods`
is Ruby's method list again and `Service.new(methods: ...)` raises
`ArgumentError`.

- Regenerate every `_connect.rb` with the 0.3.0 `protoc-gen-connectrpc-ruby`
  plugin. Files generated by 0.2 call `Service.new(methods: ...)` and fail to
  load on 0.3.0.
- Replace `ConnectRPC::Service.new(name: ..., methods: [...])` with
  `rpcs: [...]` in hand-written declarations.
- Replace `SERVICE.methods` and other `Service#methods` reads with
  `SERVICE.rpcs`.
- Steep users: the signature changes the same way.

### Breaking change: OpenTelemetry semantic conventions 1.45.0

`connectrpc-otel` emits the
[semantic conventions 1.45.0](https://github.com/open-telemetry/semantic-conventions/blob/v1.45.0/docs/rpc/README.md)
RPC attributes directly. It does not emit the old names alongside the new ones
and has no `OTEL_SEMCONV_STABILITY_OPT_IN` mode. The instrumentation scope's
`connectrpc.semconv.version` is `1.45.0`. Update dashboards, alerts and
queries that read these attributes:

| Before 0.3.0 | 0.3.0 |
| --- | --- |
| `rpc.response.status_code` | `rpc.status_code` |
| `connectrpc.request.metadata.<key>` (Connect) | `rpc.request.header.<key>` |
| `rpc.request.metadata.<key>` (gRPC, gRPC-Web) | `rpc.request.header.<key>` |
| `connectrpc.response.metadata.<key>` (Connect) | `rpc.response.header.<key>` |
| `rpc.response.metadata.<key>` (gRPC, gRPC-Web) | `rpc.response.header.<key>` |

Status code values keep their casing: `OK` on success, lower-case Connect error
codes and upper-case gRPC codes, including `CANCELLED`. Every protocol now uses
the same metadata prefixes. Response headers and response trailers are
separate: a name listed in `response_metadata:` records only response headers,
and the new `response_trailers:` keyword of `Subscriber.new` records trailers
as `rpc.response.trailer.<key>`. Move trailer names, such as a Connect unary
`trailer-x-tail` that `response_metadata: ["trailer-x-tail"]` could not
select, to `response_trailers: ["x-tail"]`. Values under names ending in `-bin`
are recorded as standard padded base64.

SERVER spans now carry `server.address`, and `server.port` when the request
gives one explicitly, from the request's `Host` or HTTP/2 `:authority`. Rack
and Rails pass `Host`, and the native Async and Falcon hosts pass the
authority. See [semantic conventions and error status](../gems/connectrpc-otel/README.md#semantic-conventions-and-error-status).

`connectrpc-sentry` span data uses the same names. Its
`rpc.response.status_code` is now `rpc.status_code`, with the same casing.
`rpc.server` spans and transactions carry `server.address` from the same
request authority, and `server.port` when the request gives one. Update Sentry
queries, dashboards and alerts that read the old name. Sentry records no RPC
metadata, so the header and trailer changes do not apply to it. See
[data and privacy](../gems/connectrpc-sentry/README.md#data-and-privacy).

Lifecycle subscribers also see trailers separately. `Instrumentation::Outcome`
has a `response_trailers` member with trailing metadata, without any
`trailer-` wire prefix, for every protocol and role. Connect unary
`Outcome#response_metadata` no longer contains the `trailer-*` header names,
and streaming client outcomes now carry the received response headers instead
of an empty snapshot. `Outcome.new` callers that omit `response_trailers` keep
working with an empty snapshot. See
[RPC lifecycle observation](design.md#rpc-lifecycle-observation).

### New service and call options

These are additive; existing code keeps working once the rename above is done.

- `binding:` is optional on `Client.new`, `Server.new` and
  `ErrorDetail#decode`. Omitted or nil, it uses the Google protobuf binding
  once `require "connectrpc/bindings/google_protobuf"` has loaded it, and
  raises `ArgumentError` naming that require otherwise. Generated `_connect.rb`
  files now require it, so code that loads a generated service can drop both
  the require and `binding:`. A custom binding is still passed explicitly.
- The Rails `connect_binding` hook defaults to nil, which selects that same
  binding, instead of raising `NotImplementedError`. Controllers that override
  it are unchanged.
- Generated services add `handlers_for(impl, strict: false)`, which maps each
  RPC to `impl`'s public method of the same snake-case name. RPCs the object
  lacks are omitted and answer `unimplemented`; `strict: true` raises
  `ArgumentError` naming them. The keyword `handlers(...)` is unchanged. See
  [the generated service API](unary.md#use-the-generated-service-api).
- `Client#call`, `#server_stream`, `#client_stream` and `#bidi_stream`, and
  the generated wrappers, accept `deadline:`. The call uses the earlier of it
  and `timeout:`, so a handler can pass `deadline: context.deadline` to a
  downstream call. Nothing propagates implicitly. See
  [deadlines](unary.md#deadlines).
- `ConnectRPC::Transports::NetHTTP.new` accepts `ca_file:`,
  `certificate_chain:` and `private_key:`, validated like the Async client
  transports' options, and `proxy:`. See
  [NetHTTP TLS and proxies](unary.md#nethttp-tls-and-proxies).
- `ConnectRPC::Keepalive` is part of core and loads with `require
  "connectrpc"`. It is the class connectrpc-async called
  `ConnectRPC::Async::Keepalive`, with the same constructor, validation,
  equality and freezing; that name remains an alias, so existing code needs no
  change. Signatures that named `ConnectRPC::Async::Keepalive` keep working.
- The new optional `connectrpc-hyper` gem adds `ConnectRPC::Hyper::Transport`,
  a client transport on a Rust extension (hyper, h2, rustls and tokio) that
  makes Connect and native gRPC calls of every shape from any thread without
  an Async reactor. It publishes prebuilt platform gems and a source gem. It
  needs a matching `connectrpc` and a prebuilt platform gem, or Rust 1.85+,
  libclang and a C compiler for the source gem. See the
  [package guide](../gems/connectrpc-hyper/README.md).
- `ConnectRPC::Async::PerCallTransport` makes Connect and native gRPC unary
  and server-streaming calls over one HTTP/2 connection per call. It takes no
  origin, keeps no connection between calls and works from any thread or
  inside a reactor. Its `proxy:` option defaults to `:environment`, which
  chooses the proxy by the request URL's scheme, as NetHTTP does:
  `HTTP_PROXY` for h2c (`http://`) targets and `HTTPS_PROXY` for TLS targets,
  minus `NO_PROXY`. Pass `proxy: nil` to always connect directly. See
  [one-off calls](../gems/connectrpc-async/README.md#one-off-calls) and
  [its proxies](../gems/connectrpc-async/README.md#proxies).
- `ConnectRPC::Async::Transport`, `ThreadedTransport` and `HTTP1Transport`
  accept the same `proxy:` option, chosen by the origin's scheme. HTTP/2
  connections and `https://` HTTP/1 origins tunnel with `CONNECT`; `http://`
  HTTP/1 origins send absolute-form requests to the proxy, as NetHTTP does.
  See [proxies](../gems/connectrpc-async/README.md#proxies).

### Behavior changes

This affects core clients.

- `timeout: 0` and negative timeouts, and `ConnectRPC::Deadline.new` with zero
  or a negative value, are an already-expired deadline: the call raises
  `deadline_exceeded` before the transport runs, as grpc-go does. Before 0.3.0
  they raised `ArgumentError`. Code that computes a remaining budget, such as
  `timeout: context.deadline.remaining`, now fails with `deadline_exceeded`
  once it reaches zero. Infinite, NaN and non-numeric timeouts still raise
  `ArgumentError`.
- Every core client sends a default User-Agent:
  `connectrpc-ruby/<version> (ruby <RUBY_VERSION>)` for Connect and
  `grpc-ruby-connectrpc/<version> (ruby <RUBY_VERSION>)` for gRPC. A
  `user-agent` in call metadata or set by an interceptor still wins, and
  `"user-agent" => []` sends none. Servers that match on the old `Ruby` value
  or on its absence need updating.

These affect the core `Net::HTTP` transport.

- It uses the proxy environment by default, as Go's `net/http` does:
  `HTTPS_PROXY` for `https://` URLs and `HTTP_PROXY` for `http://` URLs, minus
  `NO_PROXY`, `localhost` and loopback addresses. Before 0.3.0 it ignored them.
  An environment proxy with a scheme other than `http://`, such as a
  `socks5://` value set for another tool, now fails affected calls with
  `unavailable`. Pass `proxy: nil` to connect directly as before.
- It no longer sends Net::HTTP's `User-Agent: Ruby`; requests carry the client
  default above or exactly the request's `user-agent` values.
- It opens its own sockets, so it no longer calls `Net::HTTP#connect`.
  Instrumentation that hooks that method, such as the connection span of
  `opentelemetry-instrumentation-net_http`, no longer observes connection
  setup. Request spans and propagation through `Net::HTTP#request` are
  unchanged.
- TLS requires version 1.2 or later, offers ALPN `http/1.1`, and disables
  session tickets and session resumption, matching the Async client transports.
- It dials resolved addresses as Go's `net.Dialer` does, instead of Ruby's
  `TCPSocket` Happy Eyeballs: addresses of one family are tried in order, each
  with a share of the remaining deadline, and the other family starts 300 ms
  later.

These affect the Async `Transport`, `ThreadedTransport` and `HTTP1Transport`.

- They use the proxy environment by default, as `PerCallTransport` and the
  core `Net::HTTP` transport do: `HTTPS_PROXY` for `https://` origins and
  `HTTP_PROXY` for `http://` origins, minus `NO_PROXY`, `localhost` and
  loopback addresses. In a CGI process (`REQUEST_METHOD` set), a set
  `HTTP_PROXY` fails `http://` calls with `unavailable` before `NO_PROXY`,
  `localhost` or loopback is considered, as in NetHTTP. Before 0.3.0 they
  ignored the environment and always connected directly. A process whose
  environment sets a proxy for other tools now sends these connections
  through it, and an environment proxy with a scheme other than `http://`
  fails affected calls with `unavailable`. Pass `proxy: nil` to connect
  directly as before. `ThreadedTransport` reads the environment on the thread
  that constructs it.
- Their `inspect` now ends with `proxy=environment`, `proxy=explicit` or
  `proxy=direct`.

`Thread#raise` and `Thread#kill` from another thread into a thread that runs
a reactor, as Rack::Timeout does, are documented as unsupported for the Async
client transports and the Async and Falcon hosts. Earlier docs called them
best-effort for the client transports. Inside a reactor, use RPC deadlines,
Async task cancellation, `with_timeout`, or `Timeout.timeout` from an Async
task. Callers on threads that run no reactor, such as `ThreadedTransport` and
`PerCallTransport` callers outside a reactor, are not affected. See
[Interrupts inside a reactor](../gems/connectrpc-async/README.md#interrupts-inside-a-reactor).

A `ThreadedTransport` call, stream operation or `close` from an Async task no
longer defers `Thread#raise` and `Thread#kill` around its bookkeeping, and no
longer reopens them around its waits and stream blocks. Ruby applies both to
the whole thread. While such a caller waited for a lock held by the owner
thread, `SIGINT` ended `Sync` with `RuntimeError: Closing scheduler with
blocked operations!` instead of `Interrupt`, and while it waited for its reply,
`SIGINT` could land in another task's code. Callers on ordinary threads keep
both. A `close` from an Async task that is cancelled before the owner accepts
it now leaves the transport open; it used to leave the transport closing with
its owner thread running until the process exited.

These affect the Async HTTP/2 and HTTP/1 client transports and the core
`Net::HTTP` transport. Error codes are unchanged.

- An enclosing Async `with_timeout` around a client call or stream operation
  now ends it with that same `Async::TimeoutError`. Before 0.3.0 the call ran
  on under its RPC deadline, or failed as `unavailable` with a nil deadline.
  Rescue `Async::TimeoutError` where you previously rescued
  `ConnectRPC::Error` for this case. An expired RPC deadline or cancellation
  still raises `deadline_exceeded` or `canceled`.
- Client transport failures that a fixed phrase can classify now append it
  to the message, such as `HTTP/2 transport failed: connection refused` or
  `HTTP transport failed: TLS verification failed`. They also keep the
  original exception as `cause`; before 0.3.0 it was nil. Code that matches
  the exact message should match its prefix instead. Codec, compression and
  metadata errors still have no `cause`. NetHTTP proxy failures, and response
  parser errors on calls sent through an `http://` forward proxy, carry an
  internal fixed-message exception as `cause` instead, so no proxy reply text
  or credentials reach it.
- Admission failures say `... transport admission is closed` once a transport
  is closing and `... transport admission is full` at its count or byte limit,
  instead of `... admission is closed or full`.
- An invalid Async client TLS input raises `ArgumentError` naming it, such as
  `Invalid TLS client configuration: ca_file`.
- An Async client transport that is never closed is aborted once its owner
  task's block and every other task under that owner have finished. Before
  0.3.0 it kept the owner, and with it `Sync`, from finishing. Close
  transports explicitly for a graceful drain.
- `HTTP1Transport` sends a unary GET once more when its reused keep-alive
  connection closed before any response head arrived.
- The client cleanup allowance is 1 second instead of 100 ms. A reactor stall
  of up to about that long during a call's cleanup, for example from other Ruby
  threads holding the GVL, no longer fails the connection and its siblings. A
  call whose frame write is really stuck now waits up to 1 second after its
  deadline or cancellation, instead of 100 ms, before the transport forces the
  connection's retirement as before. `ThreadedTransport` callers likewise wait
  up to 1 second past a deadline, cancellation or close grace for a stalled
  owner thread. A server handler's timed request-body read that is cancelled
  also has 1 second to unwind before its connection is aborted. Server
  control-frame writes and the `too_many_pings` GOAWAY keep their 100 ms
  bounds. See the
  [cleanup allowance](../gems/connectrpc-async/README.md#cleanup-allowance).
- A `ThreadedTransport` stream operation that waited out its deadline plus
  the allowance for a stalled owner thread also ends the stream's exit wait.
  A block that rescues that `deadline_exceeded` and returns now gets it raised
  from the call at once, instead of after another allowance.

These affect native HTTP/2 connections of the Async `Transport`,
`ThreadedTransport`, `Host` and `ServerSession` and the Falcon server.

- Each connection grows its connection receive window to 16 MiB with a
  WINDOW_UPDATE on stream 0 right after its SETTINGS. Before 0.3.0 it stayed at
  64 KiB, so all streams on a connection shared 64 KiB per round trip. Host
  stream windows still start at 64 KiB, and dynamic windows, below, grow them.
  A server can now fill the windows of the streams it admits in one round trip.
  Pass `connection_receive_window: 65_536` with `dynamic_receive_windows: false`
  to keep the old connection window, since growth raises the connection window
  whenever the estimate exceeds it.
- `Transport` and `ThreadedTransport` advertise a 4 MiB stream window instead
  of 64 KiB, so one response stream is no longer limited to 64 KiB per round
  trip: a 3 MiB download over 50 ms of round-trip time takes about 0.1 s
  instead of 4 s. With static windows each call can retain up to 4 MiB of
  unread response payload, so a transport's ceiling grows from 8 MiB to
  512 MiB at the default `max_requests` of 128. Pass
  `stream_receive_window: 65_536` with `dynamic_receive_windows: false` to keep
  the old client window.
- Receive windows grow at run time, as grpc-go's do: each side sends BDP PINGs
  while DATA arrives, at most one per round trip, and raises its stream windows,
  and its connection window when needed, up to `max_receive_window` with
  SETTINGS and WINDOW_UPDATE frames. A 3 MiB upload to a default `Host` over
  50 ms of round-trip time takes about 0.5 s instead of 5 s. A peer can now
  drive a stream's unread retention up to `max_receive_window`, so the worst
  cases grow.
  - `Host`, `ServerSession` and the Falcon server default to a 1 MiB ceiling:
    1 MiB per stream, about 100 MiB per server connection at the default stream
    limit of 100, and 128 MiB across a host's 128 admitted requests. This
    departs from grpc-go's 16 MiB on purpose: gigabytes of unread request
    payload held in a Ruby process are a memory hazard that a Go server does
    not share to the same degree. It caps one upload stream at about 20 MiB/s
    at 50 ms of round-trip time and 5 MiB/s at 200 ms. Pass
    `max_receive_window: 16_777_216` to a host, or in Falcon `server_options`,
    for grpc-go's ceiling, at 16 MiB per stream, about 1.56 GiB per connection
    and 2 GiB per host.
  - `Transport` and `ThreadedTransport` default to grpc-go's 16 MiB ceiling:
    16 MiB per call and 2 GiB across a transport's 128 calls.

  Pass `dynamic_receive_windows: false` to keep static windows and the earlier
  bounds, or a lower `max_receive_window` to keep growth with a smaller
  ceiling. A proxy or peer that polices PINGs sees each BDP PING after DATA the
  other side wrote, which forgives it under grpc-go's rules. See
  [flow-control windows](../gems/connectrpc-async/README.md#flow-control-windows).
- Flow-control credit returns once a quarter of a window is pending, as in
  grpc-go, instead of half. A stream returns credit once the application has
  consumed or discarded a quarter of its window, and a connection once a
  quarter of its window has arrived. A stream whose reader keeps up therefore
  holds back less than a quarter of its window instead of up to half, and in
  the benchmark most growth steps now double its window, where more of them
  grew it by less. With static 64 KiB windows, a 3 MiB body over 50 ms of
  round-trip time takes about 2.5 s instead of 4.9 s. WINDOW_UPDATE frames
  are more frequent, depending on frame size and how the application reads:
  with 16 KiB DATA frames and a 64 KiB stream window read as it arrives, one
  per frame instead of one per three. Window sizes and retention bounds are
  unchanged.
- Forced teardown (an abort, an expired grace, or a keepalive or
  write-progress failure) shuts raw TCP down in both directions at once and
  closes the descriptor after the connection's tasks have joined. This covers
  HTTP/2 connections, Falcon's HTTP/1 connections and `HTTP1Transport`
  connections. Before 0.3.0 it closed the descriptor first, so a peer saw a
  reset whenever unread input remained. It now sees end of stream first. On
  Ruby 4 the old close could raise a stray `IOError: stream closed in another
  thread` into a task still reading the connection. The client's
  `connection_limit + max_draining` bound counts live sockets: a retiring
  socket stops counting once it is shut down, so its descriptor can stay open
  beside a replacement until the retiring connection's tasks finish.
  `HTTP1Transport` keeps a retiring connection's lease until its descriptor
  closes, as before.
- A teardown step that fails during a close or abort no longer becomes the
  caller's outcome. This covers a listener close or `stop_accepting:`
  callback, a connection's retirement and final disposal, TLS provider
  shutdown and a client transport's connection teardown. Every later step
  still runs, and the failure is written as a warning that names only its
  class, such as `ConnectRPC teardown error: Errno::EBADF`. `close` on `Host`,
  `ServerSession`, `ConnectRPC::Falcon::Server`, `Transport` and
  `HTTP1Transport` returns its drained (`true`) or forced (`false`) result,
  `ServerSession#abort` and Falcon's `Server#abort` return as usual, and
  `TLSConfiguration#close` returns the configuration. A failed listener close,
  `stop_accepting:` callback or TLS shutdown no longer skips the drain, so a
  server close returns the drain's result. A failure in a client transport's
  own close steps before or instead of the drain, such as the `Transport`
  connection manager's close, forces retirement and close returns `false`. A
  connection whose teardown fails after it drained is reported and the drained
  result stands, so a `Transport` connection whose final retirement fails, or
  an `HTTP1Transport` idle connection whose close fails after every call has
  finished, leaves close returning `true`. A Connect unary `Transport` call
  whose cleanup failed, and whose connection retirement then failed too, now
  returns its response; in 0.2.1 it raised the retirement's error instead.
  In 0.2.1 the first failure stopped the remaining steps and was raised from
  `close` or `abort`: a server session could stay closing with its TLS refresh
  timer running until the owner task ended, and a client transport could
  leave connections open. Watch for the warning instead of rescuing teardown
  errors. An interrupted caller still gets its own exception. See
  [Close results](../gems/connectrpc-async/README.md#close-results).
- A connection drain whose streams finished within the grace reports drained
  (`true`), however the peer leaves afterwards. This covers `close` on `Host`,
  `ServerSession`, `ConnectRPC::Falcon::Server` and `Transport`, and
  `drain_tls`. Close still sends the final GOAWAY, half-closes and waits for
  the peer's EOF until the grace ends, but a peer that never sends EOF no
  longer makes the result `false`. A Falcon HTTP/1 response that has been
  delivered counts as finished during its 500 ms post-response wait, so a
  grace that ends inside that wait also reports drained, and still forces
  raw-first retirement at once. In 0.2.1 both cases returned `false`. A forced
  close, `close(grace: 0)` or `abort`, still returns `false`, and so does a
  drain whose streams were still running when its grace ended. See
  [Close results](../gems/connectrpc-async/README.md#close-results).

These affect `connectrpc-otel` spans and trace propagation.

- `connectrpc-otel` uses the application's global propagator,
  `OpenTelemetry.propagation`, when `Subscriber.new` gets no `propagator:`,
  instead of a fixed W3C trace-context plus baggage propagator.
  `OpenTelemetry::SDK.configure` installs trace context plus baggage unless
  `OTEL_PROPAGATORS` says otherwise, so SDK applications keep W3C propagation
  and now also honor settings such as `b3`. An application that never sets a
  global propagator, such as one with only the API installed, now propagates
  nothing. Pass `propagator:` to keep the old behavior. See
  [what the application owns](../gems/connectrpc-otel/README.md#what-the-application-owns).
- An OpenTelemetry SERVER span whose response delivery aborted with a non-OK
  code now follows the server error policy, as a delivered response does. A
  client cancellation leaves the span UNSET with `rpc.status_code`
  `canceled` (`CANCELLED` for gRPC) and no `error.type`; it was ERROR with
  `error.type=delivery_aborted` (or `CANCELLED`). A Connect CLIENT span whose
  delivery aborted with a non-OK code reports that code as `error.type`
  instead of `delivery_aborted`. An abort after `OK` or without a code is
  unchanged. Update server error-rate dashboards and alerts that counted
  client cancellations.
- `error.type` for a failure from a non-Connect exception without an RPC code
  is the exception's class name, such as `RuntimeError`, instead of
  `operation_failed`. Anonymous exception classes still report
  `operation_failed`.

This affects the Google protobuf binding.

- The Google protobuf binding rejects a zero-length JSON payload, as connect-go
  does, instead of decoding it as an empty message. A server answers
  `invalid_argument` and a client raises `internal`. Send the message's JSON
  form instead: `{}` for an empty ordinary message, or a well-known type's own
  form, such as `""` for an empty `StringValue`. Binary protobuf still accepts
  an empty payload. See
  [the Google binding](unary.md#declare-a-method-without-generation).

These affect the Async `Host` and Falcon's native listener. See
[Connection capacity](../gems/connectrpc-async/README.md#connection-capacity)
and [Accept errors](../gems/connectrpc-async/README.md#accept-errors).

- `max_connections` defaults to 1024 instead of 128 on `Host`,
  `ServerSession` and `ConnectRPC::Falcon::Server`. Set it explicitly to keep
  the old cap, and check that the process's open-file limit leaves room for it.
- A host at `max_connections` no longer accepts and closes new peers. They wait
  in the kernel's listen backlog until a connection retires, and a full Falcon
  worker leaves them for its siblings. A client now sees a slow connection
  instead of a reset. The kernel completes the TCP handshake, so the wait is
  bounded by whatever covers the client's next step: the Async `Transport`'s
  `connect_timeout` covers TLS and the HTTP/2 SETTINGS exchange, while a
  plaintext HTTP/1.1 client needs a request or read timeout. A custom host
  that calls `ServerSession#accept(raw)` itself still has peers above the cap
  closed.
- `EMFILE`, `ENFILE`, `ENOBUFS` and `ENOMEM` from `accept` retry indefinitely
  with a delay from 5 ms doubling to 1 second and a warning per retry, instead
  of stopping the Host after six failures. `ECONNABORTED` and `EINTR` retry at
  once. Falcon's native listener used to end its accept loop on these errors
  and now retries the same way. Watch the warnings, or the open-file count,
  instead of relying on `Host#wait` to raise.
- A TLS identity that expires while it is published keeps being served, and
  the host reports `on_tls_error` category `:expired` once per generation (a
  warning without a reporter). New handshakes used to be closed before the
  ClientHello. Verifying clients now fail with a certificate-expired error.
  Handle `:expired` in reporters that switch on the category, and use the new
  `tls_status[:identity_expires_at]` to alert before expiry.
- Calling `close` or `refresh_tls` from `on_tls_error` during the `:expired`
  report raises `LifecycleError`, as it already did during a provider refresh
  report. `reload_tls` and `drain_tls` work there, so a static-TLS reporter can
  publish a replacement identity.
- Host listeners and listeners from `ConnectRPC::Falcon::Endpoint#bound` are
  close-on-exec, so exec'd child processes no longer inherit them. Pass
  `close_on_exec: false` to `Endpoint#bound` to keep the old behavior.
- `Host.new(port: 0)` binds every resolved address on one port, so
  `host.port` is the port of every entry in `host.addresses`.
- `Host#start` raises the startup error or the listener's terminal cause, and
  `Host#wait` raises that listener cause, even when the session abort or a
  listener close fails during cleanup. That failure is written as a teardown
  warning instead. In 0.2.1 `start` raised the cleanup failure in place of
  its cause, and `wait` never returned, because the failure skipped resolving
  the host's completion; a failed listener close also left the later
  listeners open. Each listener close is now attempted once, and a listener
  whose close failed may stay open.
- A caller of `Host#close`, of `close` or `abort` on `ServerSession` or
  `ConnectRPC::Falcon::Server`, or of `close` on a `ServerSession#accept`
  handle that is cancelled, times out or is otherwise interrupted gets its
  exception at once, and the drain or retirement keeps running. Before 0.3.0
  an interrupted `close` forced raw-first retirement, waited for it and then
  raised, and an interrupted `abort` raised only after retirement finished.
  A later `close` joins the running drain. To force it, call
  `close(grace: 0)`, or `abort` on `ServerSession` and Falcon's `Server`: a
  repeated `close(grace: 0)` now forces a drain whose outcome is not yet
  decided while a connection is still open, where it used to join it.
  Cancelling the task that created the host still forces teardown, and that
  task finishes only after retirement, but `Task#wait` on it can now return
  before retirement completes. See
  [Interrupted server close](../gems/connectrpc-async/README.md#interrupted-server-close).
- A `Host#start` caller that is cancelled, times out or is otherwise
  interrupted during startup cleanup, and a `Host#wait` caller interrupted
  while it waits for terminal cleanup, get the exception at once. The host's
  exit task finishes cleanup on its own, and a later `wait` raises the
  listener cause once it has. In 0.2.1 both callers stayed until cleanup
  finished: `wait` then raised the interruption, and `start` raised the
  startup error or listener cause in its place. A starter's own interruption
  now wins over a recorded listener cause. See
  [Terminal failure and startup](../gems/connectrpc-async/README.md#terminal-failure-and-startup).
- Listener shutdown on `Host` and Falcon's native listener cancels and joins
  every accept loop before it closes each listening socket, so no accept loop
  is still waiting on a socket as it closes, and concurrent shutdown steps run
  one at a time. In 0.2.1 the `Host` closed its listening sockets before it
  cancelled the accept loops, and Falcon closed them without waiting for its
  accept tasks to finish. An accept loop whose cancel fails is not joined, and
  its socket stays open.
- A `TLSConfiguration#close` caller that is cancelled, times out or is
  otherwise interrupted gets its exception at once while provider shutdown
  continues in the configuration's own task, and a later `close` joins it and
  returns once the configuration is closed. In 0.2.1 a cancellation stopped
  shutdown where it landed, so the provider's timer or callback could keep
  running until a later `close`, and a caller's own timeout landing in
  shutdown was dropped. Host and session TLS shutdown still finishes before
  their cleanup ends.
- A unary, client-streaming or fallback HTTP/2 response that waits 60 seconds
  for flow-control credit is reset with `RST_STREAM(CANCEL)` and its admission
  slot is released. Before 0.3.0 it waited until a deadline or `close`. Raise
  or disable the bound with the new `response_body_timeout:` option (nil turns
  it off). Server-streaming and bidi responses are not affected. See
  [Stream admission](../gems/connectrpc-async/README.md#stream-admission).
- An HTTP/2 connection whose single frame write does not finish within 60
  seconds is aborted, failing all of its streams. This catches peers that stop
  reading their socket, for every RPC shape. On Linux 4.6 and later, a write
  blocked on a full send buffer is renewed for another 60 seconds while the peer
  keeps acknowledging data, so a slow reader whose TCP acknowledgements keep
  advancing stays connected, and one that stops is aborted 60 to 120 seconds
  after the later of its last progress and the blocked write's start. On other
  platforms and older kernels each write keeps a fixed deadline, and a blocked
  write waits for the peer to drain a large part of the send buffer, about 950
  KB on Linux defaults, so raise the bound with the new `frame_write_timeout:`
  option for clients that read large responses over slow links. With nil the
  bound is off, and a control frame such as a PING ACK queued behind the stalled
  write still ends the connection after the keepalive `timeout`.
- An HTTP/2 stream that arrives while `max_requests` admission is full is
  refused with `RST_STREAM(REFUSED_STREAM)` while its HEADERS are read, before
  any of its DATA, instead of after its request was queued for dispatch. Its
  request body is never buffered, and an admitted stream holds its slot from
  its HEADERS. Each refusal is still observed once as `admission_rejected`
  without an HTTP status, and Falcon still counts it in `requests_total`, but
  its handle is created after the refusal. See
  [Stream admission](../gems/connectrpc-async/README.md#stream-admission).

These affect Falcon's native HTTP/1.1 Connect server and client streaming. See
[HTTP/1.1 input retirement](../gems/connectrpc-falcon/README.md#http11-input-retirement).

- When a response is ready before its request body has been read, Falcon reads
  up to 256 KiB of the unread body before it writes the response head, as Go's
  `net/http` server does, and still closes the connection after the reply.
  Before 0.3.0 it wrote the response first, discarded input for at most 100 ms
  and closed 500 ms after the final flush, so a client that paused its upload
  past that close could fail its late write and lose the response. Such early
  responses now wait for the client's upload, bounded per read by
  `request_body_timeout` (default 60 seconds, which now also applies to this
  HTTP/1.1 read) and in total by the Connect deadline. A declared
  `Content-Length` remainder of 256 KiB or more is not read. Lower
  `request_body_timeout` to answer stalled uploads sooner.
- After delivery, Falcon no longer reads further input during the 500 ms close
  delay.

These affect `connectrpc-sentry` client propagation. See
[Propagation](../gems/connectrpc-sentry/README.md#propagation).

- `trace_propagation_targets` match the request URL as `scheme://host/path`,
  as Sentry's HTTP integrations do, instead of only the host and `host:port`.
  URL strings such as `"https://api.internal"` and scheme-anchored regexes now
  propagate. Host-anchored regexes such as `/\Aapi\.internal\z/` and targets
  naming a port such as `"api.internal:8443"` no longer match; use
  `%r{\Ahttps?://api\.internal/}` or a plain host substring instead.
- On the core `NetHTTP` transport with Sentry's default `:http` patch applied,
  the subscriber no longer injects when the patch propagates the request, so
  requests carry one set of `sentry-*` baggage members instead of two. The
  duplicate set after caller baggage is gone. `sentry-trace` and the leading
  Sentry baggage already came from the patch's `http.client` span, a child of
  the `rpc.client` span.

## 0.2.0

### Breaking change: read-only transport cancellation

Only custom transports are affected. `TransportRequest#cancellation` and
`StreamRequest#cancellation` are now a read-only `CallCancellation::View`
instead of the call's mutable `ConnectRPC::CallCancellation`. The view exposes
`cancelled?`, `reason`, `check!` and `on_cancel`, which is the whole typed
`_Cancellation` SPI, so that SPI is unchanged. A transport that called
`commit!` or `close` on `request.cancellation` must stop; core completes the
call itself. `CallCancellation.with_request` passes the view through unchanged.
See [explicit cancellation ownership](design.md#explicit-cancellation-ownership).

Generated code, message encoding and protocol defaults are unchanged, and code
does not need to be regenerated.

### Behavior changes

- A server handler that returns or sends a nil response message now fails the
  call with `internal` and the message "Nil response message" on every
  protocol. Server streaming, client streaming, native gRPC and gRPC-Web unary
  previously reported `invalid_argument`, and Connect unary depended on the
  binding. A client that sends nil still gets `invalid_argument`.
- An error that core normalizes from a rescued codec, compression or header
  exception has no Ruby `cause`. The Rails controller does the same for
  exceptions that escape it. Lifecycle observers still receive the original
  failure, so read it there instead of from `error.cause`.
- A custom binding whose `decode` raises a non-codec exception, such as
  `ArgumentError`, now propagates that exception to the caller unchanged.
  Unary clients previously reported it as `internal` "Malformed response
  metadata".
- Core calls a streaming exchange's `close_send` at most once, so custom
  streaming transports no longer see a second call.
- The generator rejects a package whose root constant collides with a standard
  library constant that core loads, such as `Net`, `URI`, `OpenSSL`, `Socket`
  or `Zlib`. Output for other schemas is unchanged.
- The Async `Host` and Falcon's native HTTP/2 path enable server keepalive by
  default (`ServerKeepalive.new`). The server sends a PING after 2 hours
  without reading a frame, and sends GOAWAY `too_many_pings` to a client whose
  PINGs arrive less than 5 seconds apart three times. `idle_timeout` now drains
  an idle HTTP/2 connection with GOAWAY instead of aborting it. Pass
  `keepalive: nil` to turn off server PINGs and enforcement. See
  [Server keepalive](../gems/connectrpc-async/README.md#server-keepalive).
- The OpenTelemetry adapter writes local `error.type` classifications in lower
  case on every protocol, such as `operation_failed` and `preflight_rejected`.
  Before 0.2.0, gRPC and gRPC-Web spans reported them in upper case
  (`OPERATION_FAILED`). Only gRPC and gRPC-Web status codes are upper case.
  Update dashboards and alerts that match the old values.
- When an instrumentation subscriber injects `baggage`, the client now appends
  it after the caller's `baggage` metadata instead of replacing it, so the
  request carries both. Other injected keys still replace the caller's values.
- `require "connectrpc/async"` and `require "connectrpc/falcon"` check the
  upstream Async hooks they depend on. When one has changed, the require
  raises an error that lists each changed hook with its installed gem version
  and the versions the package was tested with, instead of failing later at
  runtime. Pin the socketry gems to tested versions until a ConnectRPC release
  supports the new ones.
